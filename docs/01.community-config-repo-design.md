# Community Config Repo — Design Document

> Date: 2026-08-15
> Prerequisites: `repo-config.md` (remote config distribution proposal, reviewed & approved 2026-08-14; this document is its ControlFlex landing plan, with all requirement-difference adaptations noted); `2026-08-11-mod-adaptation-design.md` (list/detail page UI skeleton); `2026-08-12-mod-detail-page-design.md` (detail page); `2026-08-13-compat-config-format-design.md` (compat config JSON format)
> Branch: `feature/repo-config`

---

## 1. Background & Goals

Distribute community adaptation configs via a Git repository exposed as static HTTP (jsDelivr CDN / raw.githubusercontent). The client maintains a multi-source list, syncs remote manifests locally (on-demand download, content-addressed cache, works offline), and users browse and one-click Apply community solutions into the `user` effective layer.

**Requirements mapping** (user requirement → section of this document):

| # | Requirement | Section |
|---|---|---|
| 1 | "More" menu in the top-right of the mod adaptation Panel: edit source list / sync latest configs | §8.1–8.3 |
| 2 | List page card shows the number of community variants for that mod_id on the right | §8.4 |
| 3 | Two default sources (CDN first) | Decision 1, §5.2 |
| 4 | URL auto-appends MC version + loader | Decisions 5–7, §4.1 |
| 5 | Persistent banner on detail page + community variant list | §8.5–8.6 |
| 6 | Read-only preview page + Apply + old-config backup (timestamped) | §8.7, §7.3 |

**Goals:**

- Support multiple config sources; two official built-in sources (CDN first), users may add third-party sources.
- Multi-source union: the manifests of all **enabled** sources merge into one global catalog; different content (sha256) for the same `mod_id` are parallel variants, all visible, the user picks.
- Content-addressed storage (CAS): stored by sha256, deduplicated across sources; when the same sha256 is provided by multiple sources it merges into a mirror URL list — any one successful download suffices.
- On-demand / lazy loading: sync only refreshes manifests; content files are downloaded at preview/apply time.
- The repo layer is an optional config repository (catalog) and **does not participate in effective resolution** (the `user > default` override chain is unchanged); Apply is the only activation entry point.
- Pure static-file solution: publishing is just a git push, no server needed.

**Non-goals (out of scope this round):** manifest signing / TUF-style anti-tampering (future extension); automatic GC (API only, no UI entry); field-level config merging (whole-file override between layers); XML manifests; cross-loader sync (only the current loader is synced, see decision 5); neoforge platform implementation; backup restore UI; automatic dependency installation; standalone repo catalog browsing (community solutions are only reachable via badge/banner entries of installed mods).

## 3. Overall Architecture

New package `com.ifels.controlflex.repo`, five components + one job, single responsibility, independently testable:

1. **RepoSourceManager (source management)** — reads/writes `repo/sources.json`; seeds built-in sources; derives source ids; add/remove/disable/reorder/restore-defaults; atomic writes.
2. **RepoHttpClient (download)** — HTTP GET; streaming 2MB limit; redirect following with https→http downgrade rejection; timeout control.
3. **RepoSyncEngine (sync & content fetch)** — `syncSource`: pull manifest → validate → atomically write copy + state (zero content download); `ensureContent`: multi-URL failover download → hash verify → atomic content write; `gc`: orphan cleanup; per-source mutex.
4. **RepoCatalogIndex (union index)** — builds an in-memory map `mod_id → { sha256 → {urls, metadata, providers} }` from the manifest copies of all enabled sources; provides `countVariants(modId)` / `listVariants(modId)`. No persistence; manifest copies are the source of truth; rebuilt after sync/source edits.
5. **RepoConfigApplier (apply)** — `apply(modId, sha256)`: ensureContent → backup → overwrite user → update `.applied.json` → call `ModCompatManager.reloadUserConfig(modId)`.
6. **RepoSyncJob (singleton background task)** — state machine `IDLE/RUNNING/FINISHED/FAILED/CANCELLED` + progress `(doneSources/totalSources, currentSource, currentStage)` + failure list; cooperative cancellation (modeled on `ModJarScanner`'s cancelled flag); **lifecycle owned by the service layer, not the UI layer** (running in background = closing the dialog, job continues; reopening = attach).

The only touchpoint between the repo layer and the existing compat layer: after a successful apply, call `ModCompatManager.reloadUserConfig(modId)`. The existing `ModCompatManager` loading chain (`user > mods > default`) is **not modified**.

## 4. Storage Layout

### 4.1 Remote Repository (publishing-side convention)

baseUrl points to the repo root; MC version directories isolate, loader directories partition:

```
<repo-root>/
├── 1.20.1/                 # MC version
│   ├── forge/              # loader: forge / fabric / neoforge
│   │   ├── manifest.json   # config manifest for mods under this loader
│   │   └── mods/
│   │       └── <mod1>.json # detailed mod config (pointed to by manifest paths)
│   └── fabric/
│       ├── manifest.json
│       └── mods/
└── 1.21.1/
    └── neoforge/
        ├── manifest.json
        └── mods/
```

Manifest URL = `{baseUrl}/{mcVersion}/{loader}/manifest.json`; content URL = `{baseUrl}/{mcVersion}/{loader}/{path}` (`path` relative to the manifest's directory, e.g. `mods/mod1.json`).

### 4.2 Local Directories

```
config/controlflex/compat/
├── default/                            # built-in fallback configs (existing, read-only)
├── mods/                               # provided by cfx-* bridge mods (existing, read-only)
├── repo/                               # community config repo (new, not part of effective resolution)
│   ├── sources.json                    # all sources (including built-in), see §5.2
│   ├── manifest/<source-id>/
│   │   ├── .state.json                 # per-source state, see §5.3
│   │   └── manifest.json               # byte-for-byte copy of the remote {mcVersion}/{loader}/manifest.json
│   └── content/<mod_id>/<sha256>.json  # CAS content-addressed storage (shared across sources, immutable)
├── backup/                             # apply backups (new)
│   └── <mod_id>-<yyyyMMdd-HHmmss>.json
└── user/                               # effective layer (existing) + apply tracking (new)
    ├── <mod_id>.json
    └── .applied.json                   # see §5.4
```

- Content files are immutable: present with a matching hash = already downloaded (filesystem as state), never overwritten; remote updates appear as new variant files.
- `mod_id` (regex `[a-z0-9_-]+`) is used directly as a directory name; validation is a hard precondition. Manifest `path` is never written to disk — only used to build URLs; path safety validation is retained (reject absolute paths, `..`).
- Separation of responsibilities between manifest copy and state: `manifest.json` is the byte-for-byte remote copy (strictly corresponding to `.state.json`'s `manifestSha256`), the client injects no local fields; baseUrl is a client-side concept whose single authoritative record lives in `.state.json`.
- **Loading compatibility (mandatory change, verified)**: `loadConfigLayer`'s enumeration filter is `name.endsWith(".json")` and mod_id comes from the JSON content, not the filename — if `.applied.json` were placed in `user/` it **would be parsed as a real user config** (mod_id defaulting to an empty string). The implementation must change that filter to `name.endsWith(".json") && !name.startsWith(".")` (a one-line change inside `ModCompatManager.loadConfigLayer`); `backup/` lives outside the user directory and naturally does not affect loading.

## 5. File Schemas

### 5.1 Remote Manifest `{baseUrl}/{mcVersion}/{loader}/manifest.json`

```json
{
  "schemaVersion": 1,
  "name": "ControlFlex Community Configs",
  "generated": "2026-08-15T00:00:00Z",
  "items": [
    {
      "mod_id": "jei",
      "mod_name": "Just Enough Items",
      "home_pages": [
        { "name": "CurseForge", "url": "https://www.curseforge.com/minecraft/mc-mods/jei", "description": "Project homepage" },
        "https://modrinth.com/mod/jei"
      ],
      "path": "mods/jei.json",
      "sha256": "e3b0c442...",
      "description": "JEI controller adaptation",
      "dependencies": [
        { "mod_id": "cfx-jei-extra", "mod_name": "JEI Extra", "home_pages": ["https://..."], "description": "Optional" }
      ]
    }
  ]
}
```

- `mod_id`: unique within the manifest; lowercase alphanumerics, underscores and hyphens (regex `[a-z0-9_-]+`).
- `home_pages`: optional; elements may be either full objects `{name, url, description}` (`url` required and a valid http(s) URL) or plain URL strings; both may be mixed; normalized to object form in memory.
- `path`: relative to the manifest's directory (convention `mods/<filename>.json`), used only to build download URLs.
- `sha256`: content hash — the sole basis for variant identity, dedup keys and integrity verification (64 hex).
- `dependencies`: display-only metadata; the client does not resolve dependencies nor trigger installation.
- `schemaVersion`: a higher major version → show "please upgrade the app", do not attempt parsing, the source counts as failed; `generated`: display the config update time.
- mod_id collision across sources (with different sha256) = variants of the same mod, merged by sha256 — the community coordinates naming itself, the client does no ownership arbitration.

### 5.2 Source List `repo/sources.json`

```json
{
  "schemaVersion": 1,
  "sources": [
    { "baseUrl": "https://cdn.jsdelivr.net/gh/ControlFlexMC/cfx-compat-configs@main", "enabled": true, "builtin": true },
    { "baseUrl": "https://raw.githubusercontent.com/ControlFlexMC/cfx-compat-configs/refs/heads/main", "enabled": true, "builtin": true }
  ]
}
```

- Ordered array; order determines metadata ownership and URL attempt order (carried over from the original proposal); `enabled=false` sources do not participate in sync or the union.
- Seeds the two built-in sources on first run; on load, illegal entries (non-http(s), no host) are ignored with a warning and do not affect the other sources; a corrupted file falls back wholesale to the default two sources (logged).
- "Restore default sources": re-enable the two built-in sources, restore the default order (CDN first), user-added sources stay after them.

**Source id derivation** (carried over): after lowercasing everything —

1. host is `cdn.jsdelivr.net` and path[0] is `gh` → `${path[1]}@${host}`;
2. has path segments → `${path[0]}@${host}`;
3. no path segments → `${host}`;
4. still conflicting → `-1`, `-2` suffixes in list order.

| baseUrl | Source id |
| --- | --- |
| `https://cdn.jsdelivr.net/gh/ControlFlexMC/cfx-compat-configs@main` | `controlflexmc@cdn.jsdelivr.net` |
| `https://raw.githubusercontent.com/ControlFlexMC/cfx-compat-configs/refs/heads/main` | `controlflexmc@raw.githubusercontent.com` |

- Deleting a source = removing that entry from the array; its `repo/manifest/<source-id>/` is deleted after matching baseUrl in `.state.json`; content is shared across sources and therefore not cleaned on source deletion — left to manual gc.

### 5.3 Per-Source State `repo/manifest/<source-id>/.state.json`

```json
{
  "schemaVersion": 1,
  "baseUrl": "https://cdn.jsdelivr.net/gh/ControlFlexMC/cfx-compat-configs@main",
  "mcVersion": "1.20.1",
  "loader": "forge",
  "lastSyncAt": "2026-08-15T10:00:00Z",
  "manifestSha256": "ab12cd34..."
}
```

- `mcVersion`/`loader`: the directory segments actually used by this sync. Content URL construction **must use these recorded values**, not re-detect with current code — prevents 404s during the mixing period after future version-detection changes.
- `manifestSha256`: sha256 of the manifest copy (strict byte correspondence), used to quickly detect manifest changes; absent/null when the remote 404s (source has no current version directory).
- Single-category model (current loader only), no `manifests` category mapping or `layoutVersion` from repo-config.md.

### 5.4 Apply Tracking `user/.applied.json`

```json
{ "schemaVersion": 1, "applied": { "jei": "e3b0c442..." } }
```

- Records the applied variant sha256 per mod_id; atomically updated on apply (tmp+rename).
- On display, compare against the on-disk hash of `user/<mod_id>.json`: match → `applied`; mismatch → `modified`; no record → `untracked`.
- A corrupted file falls back to an empty record (everything shown as untracked), does not affect resolution/apply; logs a warning.

## 6. Sync, Content Fetch & Cleanup

Trigger: after client initialization, an async silent sync (one-shot via `Services.LIFECYCLE.onKeyMappingsReady`, does not block startup, reads served from the local cache first; verified available on both fabric/forge sides); plus manual "Sync latest configs" (§8.3). Both share the singleton `RepoSyncJob` (decision 14). At most one sync task per source at any time (per-source mutex); different sources may run in parallel.

### 6.1 Per-Source Sync (syncSource) — manifest refresh only, zero content download

1. `GET {baseUrl}/{mcVersion}/{loader}/manifest.json` (connect 5s / read 30s; follow 301/302, reject https→http downgrade; 2MB streaming limit).
2. Parse + validate (schemaVersion, mod_id uniqueness and legality, path safety, sha256 format).
3. Atomically write `manifest.json` (byte-for-byte copy) → atomically write `.state.json` (with the mcVersion/loader used and the manifest hash).
4. 404 → info level "this source has no manifest for the current version" (not a failure), keep the old copies; network failure / parse failure / over-limit → source fails (recorded in the job's failure list), old copies kept and keep participating in the union.

> CDN caching facts (carried over, verified conclusion from the original proposal): jsDelivr caches `@main` branch references for ~12 hours, raw.githubusercontent ~5 minutes — the manifest and sub-files may come from different cache nodes, causing version inconsistency; this design absorbs it naturally via failover ("downloaded file hash mismatches the manifest → this URL fails → switch to the next mirror URL"; the two official sources mirror each other).

### 6.2 Content Fetch (ensureContent(modId, sha256, urls)) — lazy loading at preview/apply time

1. `content/<modId>/<sha256>.json` exists → hash re-check: match → return immediately; mismatch (tampered/corrupted) → delete the bad file and continue.
2. In urls order (source-list order; URL = `{baseUrl}/{state.mcVersion}/{state.loader}/{path}`, generated and deduplicated at CatalogIndex build time), one by one: download (2MB streaming cap) → verify sha256 → the first success is atomically written to disk (tmp name contains a unique random segment + rename; concurrent downloads of the same variant do not interfere) and returned.
3. A single URL failure immediately moves to the next; URLs that hit the over-limit (TooLarge) error are dropped for this round (deterministic error).
4. All URLs in the round fail → retry the whole round after exponential backoff, at most 2 rounds; still failing → error reported, local state unaffected.

### 6.3 Manual Cleanup (gc) — API only, no UI this round

- Orphan determination: content `(mod_id, sha256)` not referenced by any enabled source's current manifest copy; manifest directories whose `.state.json` baseUrl is not in the current source list are orphans too.
- `gc()` first returns the orphan manifests for confirmation, deletes after confirmation; also cleans leftover `*.tmp` (skips fresh tmp files with an mtime within one minute).
- The sync flow never auto-deletes content.

### 6.4 RepoSyncJob (singleton)

- State machine `IDLE/RUNNING/FINISHED/FAILED/CANCELLED`; progress fields `(doneSources, totalSources, currentSource, currentStage)` and failure list; the UI polls every tick.
- Cooperative cancellation: set the cancelled flag, download sites check and exit early (modeled on `ModJarScanner`).
- Source list change (newly added / re-enabled source) → after saving, trigger a new job (silent, no progress dialog); if a job is currently running, queue until it finishes (keeps the singleton job model; simple progress display and cancellation semantics).

## 7. Browse, Select & Apply

### 7.1 Union Index (RepoCatalogIndex)

Built in memory (at startup / after sync / after source list change), merged from the manifest copies of all **enabled** sources:

```
mod_id -> {
  sha256 -> {
    urls[in source order],
    modName/homePages/description/dependencies[from the first providing source],
    providers[source-id...]
  }
}
```

- A source's manifest copy missing/corrupted → skip that source (log a warning), the rest of the union unaffected.
- At index build time, generate each variant's complete URL list (built with each source's `.state.json` mcVersion/loader) and deduplicate.
- On rebuild, construct the new instance on a background thread and atomically swap the reference when done (volatile single reference); readers always get a consistent snapshot.

### 7.2 Queries

- `countVariants(modId)` → variant count (list page badge, detail page banner).
- `listVariants(modId)` → variant list; each item includes sha256, metadata, providers, `downloaded` (content exists), and the three-state label `applied`/`modified`/`untracked`; deterministic ordering: ascending position of the first providing source in the source list → same position sorted by sha256 lexicographically.

### 7.3 Apply (apply(modId, sha256))

1. `ensureContent` (lazy loading + mirror failover).
2. `user/<modId>.json` absent → atomically copy the content file directly; present with an on-disk hash **equal** to the content hash → skip the copy (idempotent, no backup produced); present and **different** → first copy the old file to `backup/<modId>-<yyyyMMdd-HHmmss>.json` (on target name collision append `-1`, `-2`), then atomically overwrite `user/<modId>.json`.
3. Atomically update `user/.applied.json`.
4. `ModCompatManager.reloadUserConfig(modId)` takes effect.

Any step fails: neither user nor backup is touched (backup precedes overwrite; a redundant backup file from a failed overwrite is harmless), error returned.

## 8. UI Design

All new UI follows existing patterns: dialogs modeled on `AddAdaptationPopup`'s Host mode (`renderOverlays`/`mouseClicked`/`consumeEscape` hooks), the progress bar modeled on its `SCAN_BAR_H=4` style, scrolling/hover/drawing reuse `GuiHelper` primitives, copy goes through i18n (§11).

### 8.1 List Page "More" Menu (requirement 1)

Change `GuiHelper.shouldShowMoreMenu(CAT_MOD_ADAPT)` from `false` to `true`, reuse the existing `MoreMenuButton` + `MoreMenuHandler` from `SettingsScreen` (verified: menu item actions execute synchronously inside `handleClick` and the menu closes afterwards; opening a dialog from a menu item has no conflict; the dialog rendering must push its own z, modeled on `AddAdaptationPopup`'s `TOOLTIP_PANEL_Z`). Two menu items:

- **Edit source list** → opens `SourceListModal` (mounted by `ModListPanel`)
- **Sync latest configs** → opens `SyncProgressModal` (mounted by `ModListPanel`)

### 8.2 SourceListModal (requirement 1.1)

- Scrollable list, one row per source: `[↑][↓]` reorder buttons ｜ source name (host + path summary; built-in sources carry a "built-in" marker) ｜ enable toggle ｜ delete button (**greyed out for built-in sources**).
- Each row shows that source's last sync time (from `.state.json`).
- Bottom: **Add source** (`EditTextField` for baseUrl input, confirm only when a valid http(s) URL; verified that `EditTextField` is a plain class with absolute-coordinate rendering and can be used directly inside dialogs), **Restore default sources**, **Close**.
- Deleting a source takes effect immediately, no confirmation dialog (cache is re-downloadable, sources re-addable).
- Closing saves: atomically write `sources.json` → rebuild `RepoCatalogIndex` → newly added / re-enabled sources trigger a background sync (silent, §6.4).
- Implementation notes (verified): dialog click hit-testing must be dispatched in `ModListPanel.mouseClicked` before toolbar/card dispatch; `SettingsScreen` has no underlying hover masking enabled, so the dialog must mask underlying hover itself (modeled on `ModListToolbar.shouldMaskListHover`).

### 8.3 SyncProgressModal (requirement 1.2)

- Title "Sync latest configs"; progress bar + status text (`Syncing source 2/3: ControlFlexMC (cdn) — downloading manifest…`) + scrollable failure list (one line per source).
- Buttons: **Stop updating** (cancel the job → shows "stopped" → close), **Run in background** (closes the dialog only, the job continues).
- After job completion the dialog shows a summary (`Sync complete: 2 succeeded / 1 failed`).
- Reopen rules: job running → **attach** to the current job and show live status, do not restart; not running → start a new job. Refresh state from the job every tick.

### 8.4 List Page Card Badge (requirement 2)

In `ModListPanel.renderCard`, render a count pill left of the chevron: show the number when `countVariants(modId) > 0`, with a hover tooltip "N community adaptation solutions"; nothing when there is no data. The index rebuilds on sync/source edits, refreshed every tick.

### 8.5 Detail Page Persistent Banner (requirement 5)

In `ModDetailScreen`, below the header and above the info row, a full-width strip (about 16–18px tall, distinct background color):

- N > 0: "Found N community adaptation solutions" → clickable, opens `VariantListModal` (mounted by `ModDetailScreen`);
- N = 0: "No community adaptation solutions found" → not clickable.

Persistent (including the N=0 state); the count updates live as the index rebuilds.

### 8.6 VariantListModal (bridging requirements 5 and 6)

Scrollable list, one row per variant: `mod_name` + short sha256 (first 8 chars) ｜ source providers marker ｜ state label (`✓ applied` / `modified` / `downloaded` / `not downloaded`) ｜ one-line truncated description. Clicking a variant → close the dialog and push `CommunityConfigPreviewScreen` (navigation modeled on `openModDetailScreen`).

### 8.7 CommunityConfigPreviewScreen (requirement 6, read-only)

- Extends `SettingsFullScreenBase` (black background + header band structure), title "Community adaptation preview".
- **`Apply` button in the top-right corner** (position/size modeled on `MoreMenuButton`, inside the header band).
- Content top to bottom:

## 9. Error Handling

| Scenario | Handling |
| --- | --- |
| Source manifest fails (network/parse/over-limit) | The source is recorded in the job's failure list (warning logged), old copies keep participating in the union, old catalogs remain browsable and applicable |
| Source has no current mcVersion/loader directory (404) | info level "this source has no manifest for the current version", not counted as a failure; old copies kept |
| ensureContent all URLs fail | Preview page shows an error + retry; apply reports an error; the user layer and existing content files are unaffected |
| Response exceeds 2MB | Streaming detection drops it immediately (deterministic error, no retry); manifest over-limit goes through the manifest-failure path, content over-limit drops that URL |
| Content file tampered/corrupted | Hash re-check before use detects it → delete the bad file → ensureContent re-downloads (self-healing) |
| Killed mid-download | tmp is written only after verification; rename is atomic — official files are never half-written; leftover tmp cleaned by manual gc (tmp names contain a unique random segment, no mutual overwrite) |
| `.applied.json` corrupted | Fall back to empty records (warning logged), does not affect resolution/apply |
| `sources.json` corrupted | Wholesale fallback to the default two sources (logged); illegal entries are filtered without affecting the rest |
| Disk write failure | Abort the current operation; all writes are tmp+rename, existing files unaffected |

> **Invariant**: no failure leaves the local cache worse than before the failure — either a complete replacement succeeds, or everything stays as-is.
> **Observability**: all silent-degradation paths log WARNING via `ControlFlexLogger`; behavior unchanged, visibility only added.

## 10. Test Strategy

- **Unit tests**: manifest parsing/validation (bad JSON, unknown schemaVersion, path traversal payloads, illegal mod_id/sha256, home_pages object/string/mixed forms and illegal URLs, dependencies array and single-object compatibility); source id derivation (default rules / jsDelivr special case / lowercasing / no path / conflict suffixes); sources.json corruption fallback / illegal entries / restore default sources / built-in source deletion rejected; CatalogIndex (union, same-sha256 dedup and URL merging, metadata first-source-wins, providers, skipping bad copies, excluding disabled sources); applied tracking (three states, corruption fallback); backup naming and collisions (`-1`/`-2` suffixes); apply four branches (absent / identical / different+backup / failure touches nothing).
- **Integration tests** (local `com.sun.net.httpserver` stub): sync pulls only the current loader's manifest with zero content requests; 404 = info, not failure, old copies kept; source network failure isolation; ensureContent multi-URL failover (first down → second succeeds, all down → whole-round retry, over-limit dropped); concurrent apply of the same variant is safe (unique tmp names); content tamper self-healing; repeated sync idempotent (manifest unchanged → hash and copy bytes both unchanged); job cooperative cancellation; URL construction uses `.state.json`'s mcVersion/loader.
- **End-to-end acceptance** (mc-cfx MCP + local stub server or system-property-redirected official sources): the full chain — startup auto-sync → list page badge → detail page banner → variant list (three-state labels) → preview page (download progress / failure retry) → Apply → backup timestamped file generated → user file takes effect (`[ControlFlex/]` log / behavior change) → apply a different variant again → second backup; "Edit source list": add stub source / disable built-in / reorder / restore defaults; "Sync latest configs": stop updating and run-in-background (attach does not restart); offline startup (cache browsable and applicable).
- **Fault injection**: server down / byte corruption / redirect toggles; corrupted `.applied.json` / `sources.json` to verify fallbacks; pre-seeded `*.tmp` leftovers to verify gc cleanup.
